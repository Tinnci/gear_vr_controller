# Gear VR 固件与加密重连故障分析

检查日期：2026-10-01。分析对象是用户提供的 Gear VR InputService 3.2.02.1 APK
内的两份更新镜像。没有向控制器写入固件，没有重置适配器或重启 Windows。

## 当前结论

已确认更新包格式、校验和版本字段；已定位镜像中的 BLE 配对数据保存和恢复路径。
尚未读取到这台控制器的实际固件版本，也尚未确认造成密钥缺失的具体代码缺陷。
现有 HCI 追踪已将实际失败定位到链路加密阶段，详见
[蓝牙恢复调查](BLUETOOTH_RECOVERY.md)。

不能把 APK 携带的升级目标版本当作设备当前版本。也不能仅凭 `0x06`，
将根因断言为“Windows 旧配对记录”或“固件从不保存 LTK”。

## 实际版本读取

核对 Samsung APK 的 UUID 映射和读取回调后发现：

| 服务/特征 | 本次用途 |
| --- | --- |
| `180A` Device Information | 版本信息所在服务 |
| `2A28` Software Revision | Samsung 回调将其作为 `Firmware Version`，预期为 `YO324...` |
| `2A26` Firmware Revision | Samsung 回调检查原始字节 `D4 D4 D4 D4`；不能假定它就是版本字符串 |
| `2A27` Hardware Revision | 辅助硬件信息 |

一次固定 Public 地址的只读探针获得缓存服务拓扑，随后首先对 `2A28` 执行
`ReadValueWithCacheModeAsync(Uncached)`。结果为 `GattCommunicationStatus.Unreachable (1)`，
没有返回版本字节，连接状态仍为 Disconnected。另一次制造商特征的实时读取也失败。
服务拓扑来自缓存，不能作为设备当前在线或版本读取成功的证据。

探针没有配对、初始化命令、通知订阅或 GATT 写入。总超时 30 秒，首次实时读取失败后停止，
服务和设备句柄在退出时关闭。源文件和 JSONL 输出保存在本地忽略的诊断目录。

## 打包格式

两份镜像都符合 Dialog DA1468x 的 SUOTA image header，头部为 36 字节，小端整数：

| 文件偏移 | 长度 | 内容 |
| --- | --- | --- |
| `0x00` | 2 | 镜像标识 `70 61` |
| `0x02` | 2 | Flags，本次两份均为 `FFFF`，具体位含义未验证 |
| `0x04` | 4 | 可执行体大小 |
| `0x08` | 4 | 可执行体 CRC32 |
| `0x0C` | 16 | 版本字符串字段，读取到 NUL 为止 |
| `0x1C` | 4 | 创建时间戳 |
| `0x20` | 4 | 可执行体在文件内的位置，本次为 `0x24` |
| `0x24` | 剩余 | 原始可执行体 |

本地以 `zlib.crc32(image[36:])` 计算，两个结果均与头部匹配。
载荷可以直接按 ARM Thumb 解码，存在向量表和字符串；没有发现需要先解压的容器层。
不能套用 DA145xx 的其他长度头部或将 `0x20` 的可执行位置误认为加密字段。

结构依据为 [Dialog/Renesas SUOTA 官方说明，Table 16](https://s3.eu-west-2.amazonaws.com/lpccs-docs.dialog-semiconductor.com/um-b-056-da1468x_software_developers_guide/07_Software_Upgrade/Software_Upgrade.html)。

APK 更新代码从 assets 读取文件。在其中一个传输变体中，会另外追加逐字节 XOR 校验值，
并按 20 字节 GATT 数据块发送。这是传输层处理，与镜像头部的 CRC32 不同；
不能把追加校验字节计入本地镜像的可执行体。

## 芯片与反汇编定位

两份载荷均包含 `DA14681`、`Dialog BLE`、`RIVIERAWAVES-BLE`，
同时包含 Gear VR 型号 `ET-YO324` 和各自的 `YO324...` 版本。
初始栈指针为 `0x07FCF000`，复位向量为 Thumb 地址 `0x08020135`。
向量、字符串指针和代码引用一致支持把可执行体映射到 `0x08020000` 分析。
这些结果强烈支持 DA14681 平台，尚未通过设备读数确认具体芯片修订。

本次以 Capstone 5.0.9 解码固定函数区间，并追踪 PC 相对 literal load、直接调用、
条件分支和存储调用包装。字符串交叉引用扫描属于定位手段；
原始数据区偶然能被解码为指令，不能把扫描输出中的每行都视为有效代码。
以下重点路径已从函数入口、分支和返回核对。

## 密钥存储相关路径

下面的函数名称是本次分析命名，并非恢复出的原厂符号。地址为推定运行地址。

| 路径 | AQC1 | AQD4 | 观察 |
| --- | --- | --- | --- |
| 恢复存储 | `0802B550` | `0802B54C` | 检查 `BLE_KEY` 标记；读取计数；遍历记录并恢复数据 |
| 保存存储 | `0802B758` | `0802B754` | 写入 `BLE_KEY` 标记；保存记录；写入计数与 `BLE_APV` 区域 |
| 对端记录序列化 | `0802B454` | `0802B450` | 检查对端状态位，复制标识及多个可选数据段，写出记录 |
| 条件保存 | `0802B144` | `0802B140` | 根据修改标志与另一条件调用保存路径，之后清除修改标志 |
| 存储读取包装 | `0802D5DC` | `0802D688` | 经存储对象函数表调用读取 |
| 存储写入包装 | `0802D5F0` | `0802D69C` | 经存储对象函数表调用写入 |

AQD4 的初始化路径 `0802B104` 调用存储打开路径 `0802B538` 和恢复路径 `0802B54C`。
打开路径向存储查找函数传入分区标识 5；实际分区地址和大小尚未恢复，
不能直接把 SDK 示例分区表当作三星这份固件的完整 Flash 布局。

恢复路径读取存储偏移 0 的 8 字节标记，与 `BLE_KEY` 加终止字节比较；
读取偏移 8 的计数字节，并将其限制到最多 8 条。
记录位置按 `9 + index * 0x88` 计算，单条记录为 136 字节。
记录包含状态位、7 字节对端标识和若干可选数据段。
这些布局与 BLE 绑定数据存储一致，但本次尚未把各段逐一对应到 LTK、IRK 或 CSRK 的 SDK 类型。
`BLE_APV` 的标记访问位于存储偏移 `0x500`，后续为应用持久数据的恢复/保存路径。

保存路径存在“状态位允许保存才序列化对端”的条件；
因此程序有保存能力，不代表每次连接都形成了可长期重用的绑定。
条件保存也意味着还需要追踪配对完成、断开和休眠事件何时标记修改、何时触发保存。

在所检查的保存与恢复调用点，没有看到对存储读写返回值逐项检查或回读验证。
这是可继续调查的路径，但没有观察到这台设备实际 Flash 写入失败，不能将其定为根因。

对四个重点函数，比较了排除地址迁移后的指令和控制流骨架，
恢复、保存、对端序列化、条件保存分别为 222、67、103、16 条指令，两个版本均一致。
比较会归一化外部调用地址，并不验证所有被调用函数、literal 数据、ROM 或完整程序等价。
目前没有在这些路径中找到 AQD4 明确修复 AQC1 密钥持久化的证据。

[DA1468x BLE 官方说明](https://s3.eu-west-2.amazonaws.com/lpccs-docs.dialog-semiconductor.com/um-b-044-da1468x_software_platform_reference/05_The_BLE_Framework/The_BLE_Framework.html)
说明密钥和绑定数据可通过 BLE Storage/NVMS 保存，默认仅 RAM、需显式启用持久存储。
本次镜像的实际代码路径比“SDK 默认仅 RAM”这个泛化说明更直接；
不能依据 SDK 默认配置就判定三星未实现持久存储。

## 对当前故障的解释边界

实际追踪为：成功建链 → 主机请求加密 → Encryption Change `0x06` → 本机断开。
它支持本次加密请求没有获得可用对应密钥的结论，尚未证明双方哪一处状态先发生变化。

取消旧配对后首次通信收到 645 个有效数据包，而正常关闭后新进程重连立即再次失败，
且 `IsPaired=false`。因此调查必须覆盖新的连接安全状态，不能只解释最初的旧记录。
目前没有证据显示这次复发前一定发生了控制器断电；
单纯“断电使 RAM 密钥丢失”不足以解释已观察到的所有行为。

这些 SUOTA 文件包含更新后的可执行代码，既不是整片 Flash 转储，
也不包含这台设备现有的对端密钥数据库。不能从其中提取当前双方是否匹配的 LTK。
官方平台说明还指出底层 BLE 栈，包括 SMP 和链路层，位于芯片 ROM；
镜像可以含包装和补丁，但不能假定它包含全部安全协商实现。

APK 的普通连接路径查找 Android 已绑定设备，再建立 GATT。
发现的 removeBond/createBond 调用位于固件更新相关路径，
没有找到可以移植为 Windows 普通重连自动修复的既定流程。

## 下一项有判别力的实验

1. 控制器保持工作时读取未缓存的 `180A/2A28`，确认实际版本；读取失败仍按失败记录。
2. 在明确的 RGB 配对模式下建立一次真正成功的新绑定，采集首次连接的 SMP/HCI，
   核对 bonding 标志、密钥分发完成与实际加密结果。敏感密钥不写入公开报告。
3. 比较正常断开后的立即重连、休眠后重连、断电后重连，每次记录相同阶段和原因码。
4. 若立即重连就失败，优先检查首次协商是否形成绑定及 Windows 的安全状态；
   若仅休眠或断电后失败，再集中检查控制器保存/恢复路径。

首次成功连接没有采集完整原生安全协商，因此这份证据仍缺失。
当前不具备“升级固件能修复”或“已经有持久自动修复”的证明。

本地诊断目录保留静态分析脚本、选定路径比较 JSON、解码输出和实时读取结果；
原始 APK、厂商镜像和反编译源码未加入仓库。
